# 活人驗證 API 錄製摘要

來源：Tampermonkey Recorder 匯出 `tools/活人驗證.json`。此錄製包含一組驗證 request／response，以及驗證後的狀態查詢。

## 已觀察請求

### POST /api/captcha/verify — 提交驗證

| 欄位 | 值 |
| --- | --- |
| 操作 | 活人驗證－提交驗證結果 |
| 方法與端點 | `POST /api/captcha/verify` |
| Request body | `{ "challengeId": <整數>, "checked": true }` |
| HTTP 狀態 | 200 |
| 耗時 | 78 ms |
| Response | `{ "ok": true }` |

### GET /api/captcha — 查詢待驗狀態

| 欄位 | 值 |
| --- | --- |
| 操作 | 活人驗證－查詢待驗 ID |
| 方法與端點 | `GET /api/captcha` |
| Request body | 無 |
| HTTP 狀態 | 200 |
| 耗時 | 64 ms |
| Response | `{ "pendingCaptchaId": null }` |

## 已確認觸發機制

活人驗證由伺服器在任意 API 呼叫時主動要求，以 HTTP 403 回應攔截，回應體格式如下：

```json
{"statusCode":403,"code":"CAPTCHA_REQUIRED","challengeId":3504,"message":"請先完成驗證再繼續操作"}
```

`challengeId` 直接由 403 回應體提供，無需事先呼叫 `GET /api/captcha`。

實際觀察到的觸發點：狩獵（`POST /api/hunt`）API 在連續狩獵一段時間後回傳 403 CAPTCHA_REQUIRED。

## 已確認處理流程

1. 偵測到 403 + `code: "CAPTCHA_REQUIRED"`，從回應體取出 `challengeId`。
2. 送出 `POST /api/captcha/verify` 帶 `{ challengeId, checked: true }`；成功時回傳 `{ ok: true }`。
3. 驗證成功後重新排程下一輪狩獵。

## Autoy 使用規則與待補錄

- `GET /api/captcha` 回應 `{ pendingCaptchaId }` 的用途尚不確定；可能是遊戲前端的備用輪詢，Autoy 目前不使用。
- 驗證失敗（`ok: false` 或 captcha/verify 本身報錯）時停止狩獵並顯示錯誤；不重複送出。
- 其他 API（道具、鍛造等）是否也可能被 CAPTCHA_REQUIRED 攔截，尚未觀察到。

原始 JSON 僅留本機；摘要省略帳號與個資欄位。
